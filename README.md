# Strawberry

**C++23 Modules 기반의 DirectX 12 Rendering & UI Engine**

Strawberry는 Toxbox프로젝트를 c++ 모듈로 바꾼것을 기반으로 렌더링 및 UI 시스템을 설계하고 구현하는 개인 엔진 프로젝트입니다.

단순히 그래픽 기능을 구현하는 것을 넘어, 프로젝트 규모가 커질수록 중요해지는 **계층 간 의존성, 리소스 수명, GPU 동기화, 비동기 로딩,
CPU/GPU 작업 분리, 테스트 가능한 설계**를 구조적으로 다루는 것을 목표로 합니다.

현재는 기존 헤더 중심 구조를 C++ Modules 기반으로 정리하면서, 서비스와 백엔드의 책임을 분리하고 모듈 간 의존성을 명시적으로 관리하는 방향으로
발전시키고 있습니다.

------------------------------------------------------------------------

## Architecture

Strawberry는 게임 클라이언트, 엔진 서비스, 계약 계층, 백엔드 구현을
분리하는 구조를 지향합니다.

``` text
                  게임 클라이언트
                 (게임 로직 / UI)
                         |
                         v
            +-------------------------+
            |      engine service     |
            |-------------------------|
            |     Render | Input      |
            |      Audio | Asset      |
            +-------------------------+
                         |
                         v
            +-------------------------+
            |         Contract        |
            | Interface / Shared Data |
            +-------------------------+
                         ^
                         |
          +--------------+--------------+
          |              |              |
    +-----------+  +-----------+  +-----------+
    | DxRender  |  |  DxInput  |  | SDLAudio  |
    +-----------+  +-----------+  +-----------+
          |              |              |
          v              v              v
    +-----------+  +-----------+  +-----------+
    | DirectX 12|  |   DXTK12  |  |   SDL3    |
    +-----------+  +-----------+  +-----------+
```

### 계층별 역할

-   **게임 클라이언트** --- 게임 로직과 UI를 구성하고 엔진 서비스를 사용합니다.
-   **엔진 서비스** --- 클라이언트에 필요한 기능을 제공하고 엔진 차원의 정책을 담당합니다.
-   **계약 계층** --- 서비스와 백엔드가 공유하는 인터페이스 및 데이터를 정의합니다.
-   **백엔드** --- 계약을 구현하고 DirectX 12, Windows, SDL3 등의 플랫폼별 기능을 처리합니다.
-   **C++ Modules** --- 모듈 간 의존성을 명시하고 각 모듈의 책임과 경계를 명확하게 유지합니다.

서비스와 백엔드는 계약 계층을 공유합니다. 계약은 단순한 실행 단계가 아니라, 양쪽이 공통으로 사용하는 인터페이스와 데이터의 경계입니다.

------------------------------------------------------------------------

## 주요 설계 방향

### 서비스와 백엔드의 분리

렌더링, 입력, 오디오, 에셋 등의 서비스는 클라이언트에 필요한 기능과 엔진
정책을 제공합니다. 플랫폼별 구현은 별도의 백엔드에 배치하여 상위 계층이
특정 API의 세부 사항에 직접 의존하지 않도록 설계합니다.

### 계약 중심 설계

인터페이스와 공유 데이터 구조를 별도의 계약 계층에 정의합니다. 이를 통해
서비스와 백엔드의 결합도를 낮추고, 구현을 분리해 테스트할 수 있도록
합니다.

### 명시적인 의존성

모듈 간 관계를 코드에 드러내고, 불필요한 의존성과 순환 참조를 줄이는
것을 목표로 합니다. 모듈화는 파일 형식만 바꾸는 작업이 아니라 각 모듈의
책임과 경계를 정리하는 과정으로 다룹니다.

------------------------------------------------------------------------

## Rendering

렌더링 시스템은 DirectX 12를 기반으로 구성하며, 그래픽 API의 세부 구현과
상위 렌더링 정책을 분리하는 방향으로 설계합니다.

주요 구성 영역은 다음과 같습니다.

``` text
RenderService
     |
     v
 IRenderBackend
     |
     v
   DxRender
     |
     +-- RenderGraph
     +-- Scene Rendering
     +-- Shadow Rendering
     +-- UI Rendering
     +-- Debug Rendering
     +-- Composite Rendering
     +-- Resource / Upload Management
```

렌더링 관련 인터페이스와 공유 데이터는 계약 계층에 배치하고, DirectX
12에 종속적인 구현은 DxRender 백엔드에서 담당합니다. 이를 통해 서비스
계층이 그래픽 API에 직접 의존하지 않도록 합니다.

## UI System

UI 시스템(`Game.UserInterface`)은 위젯 트리 기반의 오버레이 UI 모듈입니다.
HUD, 창, 팝업, 툴팁을 대상으로 하며, 렌더링 백엔드를 모르는 상태에서
레이아웃, 입력, 포커스, 툴팁까지 스스로 처리합니다.

### 의존 경계

``` text
Game.UserInterface -> Contract.Input.Service
                      Contract.Render.UI
                      Core.Math
```

-   `DxRender`, `DxInput`에 의존하지 않습니다.
-   그리기는 `IOverlayView`, 텍스트 측정은 `ITextMeasurer`로만 접근합니다.
-   입력은 `MouseState`(순수 데이터)로 받습니다.
-   폰트와 스킨은 클라이언트가 주입하므로 UI 모듈은 알지 못합니다.

### 구조

``` text
UserInterface
 ├─ Layer: Hud < Window < Popup < Tooltip
 │    └─ Widget Tree
 ├─ InputRouter        hover / 캡처 / 클릭 / 휠
 ├─ FocusRouter        Tab 이동 / 키 버블링 / 모달
 └─ TooltipController  지연 표시 / 위치 보정
```

-   레이어는 아래에서 위로 그려지고, 위쪽이 입력을 먼저 받습니다.
-   부모가 자식을 `unique_ptr`로 소유하고, `Detach`는 소유권을 돌려줍니다.
-   라우터는 `weak_ptr` 핸들로 대상을 추적합니다.
-   콜백 중에 위젯이 파괴되어도 안전합니다.

### 레이아웃

위치는 앵커(anchor / pivot / offset)가, 크기는 축별 정책이 정합니다.

``` text
SizePolicy   Fixed  직접 지정
             Fit    내용 크기에 맞춤
             Fill   부모 크기에 맞춤
```

변경이 생기면 Fit이 아닌 가장 가까운 조상부터 두 단계로 다시 계산합니다.

``` text
MeasureTree  아래→위  자식을 먼저 재고 Fit 축 확정
ArrangeTree  위→아래  자식 위치 결정
```

-   내용 변화는 부모 체인을 따라 전파되고, 뒤쪽 형제가 밀립니다.
-   `Stack`이 배치 방식(`ArrangeChildren`)을 재정의합니다.
-   위치와 크기는 정수 픽셀로 맞춰 흐려짐을 막습니다.
-   `Text`는 측정 결과를 캐시해서 바뀐 위젯만 다시 잽니다.

### 위젯

| 분류      | 위젯                                                   |
| --------- | ------------------------------------------------------ |
| Container | `Group`, `Stack`, `RadioGroup`, `Panel`, `ScrollView`, `Backdrop` |
| Control   | `Image`, `Text`, `Button`, `Toggle`, `Slider`, `ProgressBar` |

-   `Image`와 `Panel` 배경은 9슬라이스를 지원합니다.
-   `ScrollView`는 자식을 클리핑하고 휠로 스크롤합니다.
-   `Backdrop`은 모달/팝업 뒤를 막는 전체 크기 판입니다.
-   클립 밖으로 밀려난 위젯은 그리기 명령을 만들지 않습니다.

### 입력과 포커스

-   누름은 위쪽 위젯부터 부모 방향으로 버블링되고, 소비한 위젯이 캡처합니다.
-   캡처한 위젯은 포인터가 밖으로 나가도 이동과 뗌을 받습니다.
-   뗀 위치가 그 위젯 위일 때만 클릭입니다.
-   Tab / Shift+Tab으로 포커스를 옮기고, 키는 부모 방향으로 버블됩니다.
-   `Backdrop`은 모달이라 포커스와 키를 자기 안에 가둡니다.

### 툴팁

-   같은 대상 위에 일정 시간 머물면 뜹니다.
-   말풍선은 클라이언트가 주입한 팩토리로 만듭니다.
-   화면 가장자리에서는 축별로 반대쪽에 놓습니다.
-   누르면 꺼지고, 대상이 바뀔 때까지 다시 뜨지 않습니다.

## Engine Services

엔진 서비스는 클라이언트가 사용하는 기능을 제공하는 동시에 엔진 차원의
정책을 담당합니다.

  서비스   역할
  Render   렌더링 요청과 렌더링 백엔드 사이의 연결
  Input    프레임 단위 입력 상태 제공
  Audio    오디오 요청과 오디오 백엔드 사이의 연결
  Asset    에셋 로딩 및 에셋 관련 작업 관리

서비스는 클라이언트에서 사용할 실용적인 인터페이스를 제공하며, 백엔드의
플랫폼별 세부 사항은 계약을 통해 분리합니다.

## C++ Modules

Strawberry는 C++ Modules 기반 구조입니다.

``` text
Game Client
     |
     v
Engine Services
     |
     v
Contract Modules
     ^
     |
Backend Modules
     |
     v
Platform / Core
```

모듈 구조의 주요 목표는 다음과 같습니다.

-   `import`를 통해 의존 관계를 명시적으로 표현합니다.
-   모듈별 책임과 공개 인터페이스를 구분합니다.
-   불필요한 전방 선언 및 헤더 의존을 줄입니다.
-   순환 참조를 방지하고 의존성 그래프를 점검합니다.
-   구현 세부 사항을 공개 인터페이스에서 분리합니다.

모듈화 과정에서는 코드 이동 자체보다 의존성의 방향과 모듈 경계가
올바른지를 중요하게 다룹니다.

## 개발 방향

Strawberry가 지향하는 것은 단순히 기능을 추가하는 엔진이 아닙니다.

각 계층의 책임이 명확하고, 의존 관계를 추적할 수 있으며, 테스트를 통해 변경의 안정성을 확인할 수 있는 구조를 만드는 것입니다.

**기능을 구현하는 것뿐 아니라, 기능을 지속적으로 확장하고 개선할 수 있는 구조 자체를 설계합니다.**
